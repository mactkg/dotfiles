# 基本原則

- 必要十分な成果物を探求する: コードだけでなく、コメントや、コミットメッセージ、PRも必要十分である分量・内容を追い求める。
- シンプルさを保つ: オーバーエンジニアリングしないことは前提で、シンプルさを追求する。Easyに直せるものでも、構造を見直せばSimpleにできるなら、それを検討する。

# 実装原則

- まずシンプルに書く: 最初の実装は既存の関数・クエリを素直に呼ぶことを試す。共通化・DataLoader・キャッシュ等の抽象化は、実際の重複や問題が目に見えてから次のループで検討する。
- 知らないドメイン概念は推測しない: コードベースに存在しない用語・概念を使おうとしたら、実装前に確認する。近い概念に言い換えるのではなく、正確な名前を確かめる。
- 挙動を主張する前に末端まで裏を取る: 「ここが壊れる」「こう直す」と判断する前に、実際のデータフロー（GraphQL 入力型・送信経路・resolver・呼び出し元）を辿って確認する。既定値の有無・命名など単一のシグナルから挙動を推測して修正を入れない。
- 設計・命名・スキーマの選択は違和感を出して相談する: 一案で黙って進めず、選択肢＋推奨を添えて確認する。既存コードの語彙・慣習に揃っているかを根拠にする。

# 標準チーム（全セッション既定）

役割ごとにモデルを使い分ける。**重要: main は Opus、コードを書くのは Sonnet。**

- **main（自分）= Opus**: 舵取り・方針・レビュー・QA 判断・対話に専念。コードは原則自分で書かず委譲する。
- **実装 → `coder`（Sonnet）に委譲**: コードを書くのは Sonnet のサブエージェント。main は仕様を渡し、返ってきた diff を実ファイルで検証する。
- **UI/挙動の QA → `qa`**、**デザイン整合 → `designreviewer`** に委譲。
- サブエージェントの報告は鵜呑みにせず、実 diff / 実行結果で検証する。
- 些末・対話的なやり取りや、ごく小さな機械的修正は main が直接行ってよい。
